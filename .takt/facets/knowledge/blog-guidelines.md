# Blog Guidelines（記事執筆ガイドライン）

> このファイルを変更する前に `.kiro/workflows/blog-writing.decisions.md` を読むこと。記録された決定に反する変更（ルールの削除・元の形への巻き戻し）をしない。

## 記事の目的

- 新しいAWSサービスや機能を素早く試して、ハマりポイントも含めて正直に共有する
- 読者が実際に手を動かして再現できる情報を提供する
- 読者と同じ目線で学んでいく姿勢を持つ

## やること

- 企画で指定されたテーマ・構成に従う
- 既存記事の文体・トーンに合わせる
- コードは再現可能なレベルで記載する
- 企画メモに画像ファイルの参照（`![説明](ファイル名.png)`）があれば、そのまま該当箇所に置く。メモに画像がなく、スクリーンショットや図を入れるべき箇所には `<!-- TODO: screenshot - ○○の画面キャプチャ -->` のようなマーカーコメントを挿入する（AIは画像を作成できないため）
- 技術的に不明な点はWeb検索で確認する
- ハマりポイントやエラーは隠さず記録する。ただし環境準備の些末なトラブル（CLI のバージョンが古くてコマンドがない等）はハマりとして書かず、前提知識・条件に「事前に最新版へアップデートしておきます」程度の 1 行で済ませる
- 実行結果は文章で説明するだけでなく、実際の出力（JSON・エラーメッセージなど）を載せる。比較の前後（失効前後など）で一覧が変わる場合は、変わった後の出力も載せる。ただし、同じ形式で数百行になる出力（JSON など）は 1 回分だけ載せ、2 回目以降は差分の要点を文章で書く
- 一覧を返すコマンドの出力は、確認したい性質が読める先頭の数件（目安 5 件）に絞り、コマンド側にも件数の指定（`[:5]` など）を付ける。件数や合計は、主張に使わない限り載せない。主張と関係のない件数の差は見せない
- 出力中の ID を `tkn1...` のように省略しない。本文で ID に触れるときも実際の値を書く
- 公式ドキュメントに由来する主張には、根拠の URL を付ける。ページ全体ではなく該当節のアンカー付き URL（`#access-...` など）を、その主張を書いた段落の直後に単独行で置く。コマンドの引数一覧だけのリファレンス URL は付けない（D-43）。URL を実際に開き、内容が記述と合うことを確認してから載せる。確認できない主張は、断定せず「見つけられませんでした」と書く
- 機能がパブリックプレビュー中、または対応リージョン・サービスを段階的に広げている段階なら、前提知識・条件に「プレビュー中で仕様が変わる可能性がある」旨を 1 行書く。企画資料・公式ページに記載がなければ書かない
- 構成は最小にする。検証の目的を示す手順だけを Step にし、成功の再確認だけの Step や、「使ってみて気付いた注意点」のような独立した節は作らない。気付きは「まとめ」の箇条書きに書く
- 記事の主題（新機能・検証対象）に関わる部分だけを本文のコードにする。読者が既に知っている機能（Custom event bus、IAM ロール、DLQ など）は本文から外す。コードは新しい点を含む抜粋だけ本文に置き、全体は `<details>` の折りたたみに載せ、Step の最後に「全文は次の折りたたみに載せています。」と 1 文で案内する。コマンド 1 行だけの手順（デプロイなど）は独立した Step にせず、次の Step の冒頭で 1 文触れる
- コードの特定の行についての補足（型にないので上書きする理由、指定した値の意味など）は、そのコードブロックの直後に書く。折りたたみや別のコードを間に挟まない
- 検証の前提として効く情報だけを本文に書く。実行ロールの権限の説明、レイヤーの `pip install` コマンドと入ったバージョンなどの手順の詳細は本文に載せず、全体は折りたたみのコードに置く。結果に影響する要件（必要な boto3 のバージョンなど）だけ 1 文で残す（D-32）
- 動作確認の出力が、後の測定結果と数値が食い違って見える（初回ミスだけ遅い値など）場合は載せない。Step の出力は、主張に要る行だけに絞る（D-33）
- 測定範囲などは、関数名・内部名（`perf_counter`、`bench` など）でなく、読者に見える動作で書く（例: 「`get_item` を呼んでから結果が返るまでの時間」）。専門用語の統計値（p50 など）は、初出に 1 回だけ括弧で意味を補う（D-35）
- まとめの締めは、先に良い面（手軽さなど）を書き、「その一方で」に続けて限界と未検証の範囲（例: VPC 内は未検証）を書く。期待した効果が見えなかった原因は、推測と断って書く。題材の一例（フィーチャーフラグなど）は結論に持ち込まない（D-37）
- 機能のメリットは、発表文の伝聞（「〜と説明されています」「〜ようです」）で済ませず、何が減る・何ができるかの仕組みを 1〜2 文で書く（例: アプリと DB の往復が減る）
- サポート範囲・対応文などの仕様は箇条書きで並べ、各項目に短い説明を添える（例: `CALL`：プロシージャの呼び出し）
- 題材が実務の要件を簡略化しているとき（年末年始の休業日を入れない等）は、動作確認のために省いた旨を 1 文書く
- 見出しや説明は平易な言葉にする（「境界ケースで呼び出す」より「動作確認」）。期待値は「〜になるはず」ではなく「〜になる」と書く
- コードブロックの前は「以下のような関数を作成します。」程度の 1 文にし、ロジックの解説はコードの後に書く
- 「この記事で学べること」「前提知識・条件」を冒頭に含める
- 前提知識・条件は簡潔に（記事の日付と検証環境を1〜2行程度）
- 「同じ」「違う」と書くときは、比較する両方の実出力を載せる。片方だけ載せて「もう片方と同じ」とは書かない（D-47）
- 割合を出す式は、各項に単位を付け、上限値などの項に括弧で名前を添える。例: `600 回/分 ÷ 60 秒/分 ÷ 100 回/秒（クォータ値） = 0.1（10％）`（D-50）
- 結果の数値は、本文の入力から読者が導けるように書く。送信件数・ペースから結果の値を導く計算を、結果の前に書く（D-51）
- 順序が保証されない出力（`get-metric-statistics` の `Datapoints` など）は、コマンドに並べ替えを指定し、出力も並べ替え後のものを載せる（D-52）
- 記事の主題から読者が期待しそうな範囲を本文が満たさないときは、はじめにで 1〜2 文で断り、扱う範囲を示す（D-53）
- 所要時間は、秒単位の実測値や実行時刻でなく「約 5 分」のように丸めて書く（D-46）

## やらないこと

- 企画にないテーマや内容を勝手に追加しない
- 本題（検証対象と、結論に必要な説明）以外は書かない・書き足さない。迷ったら削る。次は 1〜2 文にまとめるか書かない: 検証対象でない準備手順（IAM ロールや関数の作成など。検証の前提になるコマンドだけ残す）、エラーが出た流れや書式の試行錯誤（動く形だけ載せる）、コマンドを見れば分かる API 名の解説や比較、あとの節で出てくる内容を「はじめに」で先に言い直す説明
- 技術的に不確実なことを断言しない（「〜の模様です。」と書く）
- 特定の技術やツールを不当に批判しない
- 他の技術との優劣比較で一方的な結論を出さない
- 過剰な箇条書きで文章を構成しない（適度に文章で繋ぐ）
- 同じ語尾を3回以上連続させない
- 「以下の通りです」「については」を多用しない
- 段落を長くしすぎない（1〜3文程度で改行。詰め込まず短く区切る）
- UI 手順を番号付きリストで長々と書かない（スクリーンショットマーカー + 短い説明の方がよい）
- セクション見出しに「過去記事の紹介」のような汎用的な名前を使わない（具体的なトピック名にする）
- コンソール画面を、画面構成の列挙（上から○○、△△が並ぶ）や各欄の説明で逐条解説しない。画像を載せたうえで、読者が見るべき点と、CLI との違いを 1〜3 文で書く
- 「見るべきところは限られます」のような予告だけの前置き、伏せ字の宣言、実行環境の細かな補足（CLI のバージョン差など）を本文に書かない
- 小さな比較（2 項目×2 行程度）を表にしない。文章 2〜3 文で書く
- 検証の手順に関係しないドキュメント情報や裏話を書き足さない（手順で使わない制約値、データ件数の内訳や照合結果、題材を選んだ理由、将来の掲載予定など）
- 「後片付け」の節を作らない
- 原因の推測や、結果からの推論を付け足さない（まとめの締めで、期待した効果が見えなかった原因を推測と断って書く 1 文は除く。D-37）（「ドキュメントの更新が追い付いていない模様」「この記事では〜を正とします」「〜ということにはならないみたいです」）。食い違いは事実と確認日だけ書く
- まとめで、検証しなかった範囲を網羅的に断らない（「N=1 のみの検証」「〜は今回動かしていない」）。結論が環境に依存する検証だけ、結論に効く範囲（検証した環境と未検証の環境）を締めの文で書く（D-37）
- 読者が自分の環境でそのまま使えない文字列を残さない。非公開プロジェクトを前提にした記述（デプロイコマンド、`packages/` などリポジトリ内のパス、非公開のスクリプト名、「context を渡して再デプロイ」）を、本文・折りたたみのコード・コード内コメント・`<summary>` に書かない。`<summary>` はファイル名だけにする（D-31）
- ドキュメントで確認していない表現を断定しない。「〜では作れません」は確認できた事実と時点に合わせて書き（「執筆時点のプロパティ一覧にはありませんでした」など）、メトリクスの意味づけは確認した名称で書く（D-34）
- 制約事項の紹介で「結構あります」「それなりにあります」のような主観的な量の表現を使わない
- サービスが自動で行う処理（バケットポリシーの自動追加など）の中身は書かない。「自動で追加される。自分で書く必要はない」程度の 1 文にする（D-44）
- 「新しい」「今回追加された」は、アップデート紹介や公式ドキュメントで確認できたときだけ書く。確認できなければ、確認できた事実だけを書く（D-48）
- 「ポイントは〜です」、「ここで想定外のことが起きました」のような劇的な導入、それに続く「…！」を使わない。想定外だったことは、何が出なかったか、その時の状況、仕様から見た原因の順に事実で書く。SQL 文の意味で単独の「文」と書かず、「SQL」と書く（D-45）

## 機微情報の扱い

- 伏せる（`XXXX` に置き換える）のは、IP アドレス、トークン本体（JWT・リフレッシュトークン）、パスワード、AWS アカウント ID、個人のメールアドレス
- 検証用に作ったリソースの ID（ユーザープール ID、クライアント ID、セッション ID、`sub`、`jti` など）は伏せずにそのまま載せる
- コマンドの `<クラスタ ID>` のようなプレースホルダーも、検証用リソースの実 ID に置き換える。出力は実 ID、コマンドはプレースホルダー、という食い違いを作らない（D-49）。アカウント ID とバケット名は伏せる
- そのかわり、記事の公開前に検証用リソースを削除する（ID が残ったリソースを第三者に操作されないため）

## 記事の品質基準

### 技術的正確性
- コマンド、設定値、API仕様が正確であること
- コード例が実際に動作すること
- 手順通りに進めて再現できること
- 最新バージョンの情報であること

### 読みやすさ
- 段落は1〜3文を目安。短く区切る
- コードブロックの前後に説明文を書く
- 長い手順はステップに分割する（コンソール操作とCLI操作はサブステップで分ける）
- 適切に見出し・箇条書き・テーブルを使い分ける

### 人間らしさ
- 著者の個性（語り口、感想、ユーモア）が出ていること
- テンプレート的な表現を繰り返さないこと
- 読者への語りかけが自然であること
- 失敗や試行錯誤のプロセスも含めること

## 記事評価の7つの観点

記事は以下の7観点で評価される（詳細は docs/blog-evaluation.md を参照）:

1. 防御力 — 主張の論理的信頼性、前提条件の明示
2. 思考整理力 — 論理的構造化、読者が思考を追体験できるか
3. 実践応用性 — 再現可能な手順、具体的なコード例
4. 構成と読みやすさ — 見出し階層、段落、視覚的要素の活用
5. コミュニケーション力 — 親しみやすさ、読者との距離感
6. 炎上リスク・社会的配慮 — 誤解を招く表現、断定的表現の回避
7. 人間らしさ — AIっぽさの排除、著者の個性

## 出力先

- 記事ファイルは `blog_content/` 配下に作成する
- ファイル名は `blog.md`
