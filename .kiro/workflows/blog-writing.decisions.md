# blog-writing ワークフローの決定記録

このワークフロー（`blog-writing.workflow.json`、`.kiro/agents/` のエージェント定義、`.takt/facets/knowledge/` の writing-style.md / blog-guidelines.md / anti-ai-smell.md）を見直すときは、先にこのファイルを読むこと。

ここに記録した決定は、実走やユーザーの手直しで理由が確認されたもの。一般的なベストプラクティスと逆向きのものもあるが、意図的な決定である。決定に反する変更（ルールの削除・元の形への巻き戻し）をしない。変える必要があるときは、ユーザーに確認したうえで、該当する決定をこのファイルで更新する。

## D-01: ループの終了条件は review.json の loopAction で判定する

- 対象: `blog-writing.workflow.json` の repeat の `stopCondition`、aggregate / fix / polish / lint-fix の prompt
- 決定: stopCondition は `review.json` の `loopAction == "exit"` を見る。verdict が APPROVED なら exit。ユーザーがループ終了を指示した場合は、verdict を CHANGES_REQUESTED のまま、loopAction だけ exit にする。fix / polish / lint-fix は loopAction が exit なら何もしない。
- 理由: verdict == APPROVED を条件にしていたときは、ユーザーが残りの指摘を受け入れて終えたい場合に、ループを抜ける手段がなかった。
- 戻さないこと: stopCondition を verdict 判定に戻さない。no-op 指示を削らない（stopCondition はループ末尾で評価されるため、exit の周でも fix 以降が起動する）。

## D-02: ユーザー判断を decisions.json に累積し、レビュアーに読ませる

- 対象: aggregate と 3 レビュアーの prompt
- 決定: aggregate がユーザーの対応／却下／見送りの判断を `{{setup.output}}/decisions.json` に追記する（上書きしない）。レビュアーはレビュー前に読み、rejected / deferred の論点を再指摘しない。
- 理由: 却下理由を知らないレビュアーが、同じ指摘を毎周繰り返して空転した。実走で、2 周目以降に既決の論点が再指摘されないことを確認済み。
- 戻さないこと: decisions.json の読み込みを、ANTI-BIAS（他レビュアーのファイルを読まない）を理由に削らない。decisions.json はレビュアーのファイルではない。

## D-03: エージェント JSON の tools は実行環境のツール実名で書く

- 対象: `.kiro/agents/*.json` の `tools`
- 決定: `read_file` / `grep_search` / `file_search` / `remote_web_search` / `str_replace` / `fs_write` / `web_fetch` の実名を使う。artifacts を宣言するステップのエージェントには `fs_write` を必ず含める。
- 理由: `fs_read` / `grep` / `glob` / `web_search` などの名前は黙って無視され、エージェントがファイルを読めなかった。artifacts があるのに書き込みツールがないと、run_workflow の検証で拒否される。
- 戻さないこと: takt 由来のツール名に戻さない。

## D-04: ai-review は執筆モデルと別系統の GPT にする

- 対象: `blog-writing.workflow.json` の各ステップの `modelId`
- 決定: 執筆（plan / write）は Claude、ai-review と tech-review は GPT 系。
- 理由: 書き手と同じモデルでは、そのモデルの癖を AI 臭さとして検出できない。
- 戻さないこと: ai-review を Claude 系にしない。

## D-05: lint は markdownlint と textlint の両方を実行する（2026-11）

- 対象: `blog-writing.workflow.json` の lint / lint-fix の prompt
- 決定: `npx markdownlint-cli2 blog_content/blog.md` と `npx textlint blog_content/blog.md` を実行し、エラー 0 まで直す。コマンドは `markdownlint-cli2`（takt 版の `markdownlint-cli` ではない）。
- 理由: markdownlint だけを実行していた版では、最終出力に textlint のエラー（冗長表現、90 字超の文、助詞の重複）が 6 件残った。`package.json` の `lint` スクリプトも両方を実行する。
- 戻さないこと: textlint を外さない。

## D-06: CLI のコードブロックは各コマンドの直前に 1 行コメントを書く（2026-11）

- 対象: `writing-style.md` の「コードブロック」節
- 決定: bash のコードブロックでは、各コマンドの直前に「何をするコマンドか」を 1 行のコメントで書く。1 ブロックに複数コマンドがあれば、コマンドごとに付ける。アプリのソースなど、それ以外のコードのコメントは最小限のまま。
- 理由: ユーザーが Cognito 記事の手直しで、全コマンドへの 1 行コメントを指示した。
- 戻さないこと: 「コード内のコメントは最小限」の一般則で、CLI のコメントを削らない。

## D-07: 前提知識・条件は 1〜2 行の箇条書きにする（2026-11）

- 対象: `writing-style.md` の記事テンプレート、tech-review の prompt
- 決定: 日付・リージョン・CLI バージョン程度を箇条書きで書く。使用ツールや IAM 権限を列挙しない。tech-review はこれらの追加を求めない。
- 理由: tech-review の指摘で前提条件に jq・PyJWT・IAM 権限・プロファイルを足したところ、ユーザーが手直しで 2 行の箇条書きまで削った。
- 戻さないこと: 再現性の名目で、前提条件の項目を増やすルールを足さない。

## D-08: tech-review は本筋外の補足を求めず、未検証の話題は削除を提案する（2026-11）

- 対象: tech-review の prompt
- 決定: 記事の本筋に関係しない注意書き・補足の追加を求めない。記事が検証していない話題の記述が不正確なときは、正確に書き足すより削除を第一案にする。記述の誤りは blocking、補足の追加提案は non-blocking に分ける。
- 理由: tech-review の指摘で、パスワードのカンマ制限、有効化前の sid の注意、API Gateway JWT オーソライザーの検証範囲などを足したところ、ユーザーが手直しですべて削除した。
- 戻さないこと: 「網羅的に正確に」の方向で、補足追加を促す指示に戻さない。

## D-09: 実行結果は出力も載せ、ID を省略しない（2026-11）

- 対象: `blog-guidelines.md` の「やること」
- 決定: 実行結果は文章だけでなく実際の出力を載せる。前後比較で一覧が変わるなら、変わった後の出力も載せる。ID は `tkn1...` のように省略しない。
- 理由: ユーザーが手直しで、失効後のセッション一覧の出力を追加し、省略表記をすべて実際の ID に直した。
- 補足: 一覧の出力の行数は D-25 で絞る。D-09 は、載せた行の ID・値を省略しないという決定。

## D-10: 伏せ字は IP・トークン・パスワード・アカウント ID などに限る（2026-11）

- 対象: `blog-guidelines.md` の「機微情報の扱い」
- 決定: 伏せるのは IP アドレス、トークン本体、パスワード、AWS アカウント ID、個人のメールアドレス。検証用リソースの ID（ユーザープール ID、クライアント ID、セッション ID、sub、jti など）は伏せない。かわりに公開前に検証用リソースを削除する。
- 理由: ID まで伏せた版を、ユーザーが手直しで IP 以外すべて外した。
- 戻さないこと: 安全側の名目で、リソース ID も伏せるルールにしない。

## D-11: 環境準備の小さなトラブルは 1 行で済ませる（2026-11）

- 対象: `blog-guidelines.md` の「やること」（ハマりポイントの項）
- 決定: CLI が古くてコマンドがない等の環境準備のトラブルは、ハマりポイントとして節を立てず、前提条件に「事前に最新版へアップデートしておきます」程度の 1 行で書く。
- 理由: 「ハマりポイントも正直に共有」の方針で CLI 更新を Step 0 として書いた版を、ユーザーが 1 行に縮めるよう指示した。

## D-12: 著者の文体を AI 臭さとして指摘しない（2026-11）

- 対象: ai-review の prompt、`anti-ai-smell.md` の「例外」節
- 決定: 次は指摘しない。手順間の転換句（「次に〜してみます」「では、〜してみます」「ここから〜していきます」）、くだけた語尾（「〜かな？」「〜てますね」「〜みたいです」）、冒頭の「今回は以下のアップデートを紹介します。」、「Step N:」形式の見出し。
- 理由: ai-review の指摘で転換句やくだけた表現を削った版に、ユーザーが手直しで同じ種類の表現を戻した。既存の Qiita 記事の冒頭も同じ型。
- 戻さないこと: 一般的な AI 臭さの基準（「ご紹介します」は定型など）で、この例外を削らない。
## D-13: 公式ドキュメント由来の主張には根拠 URL を付ける（2026-11）
- 対象: `blog-guidelines.md` の「やること」、`writing-style.md` の「リンク」、tech-review の prompt
- 決定: 公式ドキュメントに由来する主張には、該当節のアンカー付き URL を、その段落の直後に単独行（Qiita）で置く。CLI コマンドはリファレンスの URL も付ける。URL は開いて内容を確認する。tech-review は根拠 URL の欠落を non-blocking で、URL と記述の不一致を blocking で指摘する。
- 理由: IAM Access Troubleshooter の記事で、ユーザーが手直しで、対応サービス・制約・取得できる内容・CLI など節ごとに根拠 URL を追加した。
- 補足: CLI コマンドのリファレンス URL を付ける部分は D-43 で取り下げた。
- 戻さないこと: 「リンクはまとめて末尾に」の形に戻さない。
## D-14: 構成を最小にする（2026-11）
- 対象: `blog-guidelines.md` の「やること」、`writing-style.md` の記事テンプレート・テーブル
- 決定: 成功の再確認だけの Step、「使ってみて気付いた注意点」のような独立した節、同形式で数百行になる出力の 2 回目以降、小さな比較表を作らない。気付きは「まとめ」の箇条書きにする。まとめは「今回の検証で分かったことは次のとおりです。」＋箇条書き＋感想 1〜2 文（2026-11 の Aurora DSQL 記事で、冒頭の結論 2〜3 文をユーザーが箇条書きに置き換えたため改訂。D-19 参照）。
- 理由: ユーザーが手直しで、最終 Step、注意点の節、2 回目の長大な JSON、比較表を削除し、まとめに統合した。レビュー指摘に沿って直すたびに記事が長くなる傾向もあった。
- 戻さないこと: D-09（実行結果は出力も載せる）を理由に、同形式の長大な出力を毎回載せない。D-09 は 1 回分の出力を省略しないという意味。
## D-15: コンソール画面を逐条解説しない（2026-11）
- 対象: `blog-guidelines.md` の「やらないこと」
- 決定: 画面構成の列挙や各欄の説明、予告だけの前置き、伏せ字の宣言、環境の細かな補足（CLI のバージョン差など）を書かない。見るべき点と CLI との違いを 1〜3 文で書く。
- 理由: ユーザーが手直しで、コンソール節の画面解説を「CLI と同等の情報だが見やすい」程度に縮め、環境補足も削除した。
- 戻さないこと: 再現性の名目で画面解説や環境補足を足すルールにしない（D-07・D-08 と同じ方針）。
## D-16: プレビュー中の機能は前提条件に 1 行書く（2026-11）
- 対象: `blog-writing.workflow.json` の plan の prompt、`blog-guidelines.md`・`writing-style.md` の前提知識・条件
- 決定: 機能がパブリックプレビュー中、または段階展開中なら、plan.md に明記し、前提知識・条件に「プレビュー中で仕様が変わる可能性がある」旨を 1 行書く。記載がなければ書かない。
- 理由: ユーザーが手直しで、公式ページの記載をもとにプレビュー中の旨を前提条件に追加した。AI 版は記載を見落としていた。
- 戻さないこと: 前提条件を 1〜2 行にする D-07 と矛盾しない。プレビューの 1 行は例外として足す。
## D-17: 手順に関係しない情報・推測・後片付けを書かない（2026-11）
- 対象: `blog-guidelines.md` の「やらないこと」
- 決定: 手順で使わない制約値、データ件数の内訳や照合結果、題材を選んだ理由、将来の掲載予定を書かない。「後片付け」の節を作らない。原因の推測や結果からの推論（「更新が追い付いていない模様」「〜を正とします」）を付け足さず、事実と確認日だけ書く。
- 理由: Aurora DSQL の PL/pgSQL 記事で、ユーザーが手直しでトランザクション制約（DDL/DML 分離・3,000 行）、祝日 35 行の内訳と CSV 照合、2026 年を選んだ理由、2028 年分の掲載予定、後片付けの節、推測の文をすべて削除した。
- 戻さないこと: 「不確実なことは『〜の模様です』と書く」の規則を理由に、推測の文を足さない。あの規則は記事の主張を断定しないためのもので、推測を足すためのものではない。
## D-18: tech-review は検証範囲の断り書きを求めない（2026-11）
- 対象: tech-review の prompt、`blog-guidelines.md` の「やらないこと」
- 決定: 「N=1 のみ検証」「〜は今回動かしていない」のような断り書きの追加を求めない。記事にも書かない。
- 理由: tech-review の non-blocking 指摘でまとめに足した断り書きを、ユーザーが削除した。D-08 と同じ方針。
## D-19: まとめの箇条書きと仕様の「項目：説明」列挙を AI 臭さとして指摘しない（2026-11）
- 対象: ai-review の prompt、`anti-ai-smell.md` の「例外」節、`writing-style.md` の記事テンプレート
- 決定: まとめは「今回の検証で分かったことは次のとおりです。」＋箇条書き。サポート範囲などの仕様は「`項目`：短い説明」の箇条書きで並べる。ai-review はどちらも指摘しない。
- 理由: ai-review の指摘でまとめの箇条書きを文章 2〜3 文に直した版を、ユーザーが箇条書きに戻すよう指示した。対応文 4 つを 1 文に詰めた版も、ユーザーが「サポート範囲の説明として」箇条書きにさせた。
- 戻さないこと: 「結論の先出し + 箇条書き展開」「項目名: 説明」の一般的な禁止で、この 2 つを指摘しない。
## D-20: メリットは仕組みで説明し、簡略化は 1 文で断る（2026-11）
- 対象: `blog-guidelines.md` の「やること」
- 決定: 機能のメリットは発表文の伝聞で済ませず、何が減る・何ができるかを 1〜2 文で書く。題材が実務の要件を省いているとき（年末年始の休業日など）は、その旨を 1 文書く。見出しは平易に（「境界ケース」より「動作確認」）、期待値は「〜になるはず」ではなく「〜になる」。コードの前は 1 文、解説はコードの後。
- 理由: ユーザーが手直しで、「発表文では〜説明されており、〜ようです」をラウンドトリップが減る仕組みの説明に、「境界ケースで呼び出す」を「動作確認」に変え、関数の解説をコードの後へ移し、年末年始を省いた旨を追記させた。
## D-21: メモの画像参照はそのまま記事に置く（2026-11）
- 対象: write の prompt、`blog-guidelines.md` の「やること」
- 決定: 企画メモに `![説明](ファイル名.png)` があれば、TODO マーカーにせずそのまま置く。マーカーはメモに画像がないときだけ使う。
- 理由: メモに画像参照が 4 つあったのに、write がすべて TODO マーカーに置き換え、ユーザーが手で戻した。
## D-22: lint は embed リンクと既決の修正を戻さない（2026-11）
- 対象: lint / lint-fix の prompt
- 決定: はてなブログの単独行 `[URL:embed:cite]` が sentence-length に検出されても、既知の誤検出として残して完了する。decisions.json で accepted の修正を lint 修正で戻さない。
- 理由: lint-fix が textlint 0 件を目指して embed を通常リンクに、ですます調を常体に戻したため、承認済みの指摘が 3 周続けて未反映になり、最後は embed を維持すると完了できずワークフローが失敗した。
- 戻さないこと: D-05 の「エラー 0 まで直す」を理由に embed を書き換えない。`.textlintrc.json` の `skipPatterns` で除外する案はユーザー確認待ち。
## D-23: 本題以外は書かない・書き足さない（2026-11）
- 対象: `blog-guidelines.md` の「やらないこと」、write の prompt
- 決定: 検証対象と結論に必要な説明以外は書かない。検証の前提でない準備手順は 1〜2 文にまとめる。エラーの経緯や書式の試行錯誤は書かず、動く形だけ載せる。コマンドで分かる API 名の解説、「はじめに」での後続内容の先出しは書かない。迷ったら削る。
- 理由: CloudWatch Logs 保持ポリシーの記事で、ユーザーが手直しで Lambda・IAM の作成手順、dryRun のエラー経緯（書式を試した表を含む）、PutRetentionPolicy と PutAccountPolicy の API 解説、「はじめに」の効き方の再説明を削除またはまとめた。
- 追補（2026-11）: 検証の結論が変わらない条件（QoS のレベル、トピック名、検証していない換算など）は書かない。判断軸は「その条件を変えると、結論が変わるか」。IoT Core のクォータ使用量の検証記事で、ユーザーが削除した。
- 戻さないこと: D-17 の「手順で使わない情報を書かない」を、準備手順・試行錯誤・API 解説にも広げたもの。再現性のためという理由で準備手順を全文載せない。
## D-24: 新しい点だけを本文に置き、読者が既に知っている部分は省くか折りたたむ（2026-11）
- 対象: `blog-guidelines.md` の「やること」、write の prompt
- 決定: 記事の主題（今回の新機能・検証対象）に関わる部分だけを本文に書く。読者が既に知っている機能の部分（Custom event bus の作成、サブスクライバー、IAM ロール、DLQ など）は、本文のコードから外す。コードは新しい点を含む抜粋だけ本文に置き、全体は `<details>` の折りたたみに載せて、抜粋であることと折りたたみがあることを 1 文で案内する。コマンド 1 行だけで読者に説明が要らない手順（デプロイなど）は独立した Step にせず、次の Step の冒頭の 1 文で触れる。判断の軸は「この部分は主題の検証に効くか、読者は既に知っているか」。
- 理由: EventBridge Scheduler の記事で、AI 版はバス・サブスクライバー・スケジュール A・B のコードをすべて本文に載せ、デプロイも独立した Step にしていた。ユーザーが手直しで、新機能と関係ない（目新しくない）バスとサブスクライバーを外し、全文を折りたたみに移し、デプロイの Step を削除した。新しい点がコードの量に埋もれるため。
- 戻さないこと: D-09 や「再現可能なレベルで記載する」を理由に、既知の部分まで本文に載せない。再現性は折りたたみの全文で担保する。D-14（成功の再確認だけの Step を作らない）の延長で、独立した Step にする価値がない手順にも適用する。
## D-25: 実行結果は、確認したい性質が読める最小限だけ見せる（2026-11）
- 対象: `blog-guidelines.md` の「やること」
