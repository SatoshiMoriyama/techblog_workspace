# 検証ブログ用の下書きメモ作成

アップデートを起点に、実機検証の前段となる `blog_content/memo.md` を作る。清書（`blog.md`）はユーザーが別工程で行う。

## 入力

- 起点の URL（What's New など）
- 投稿先（既定: はてなブログ）

不足していれば聞く。既存の `memo.md` / `blog.md` は、指示がない限り上書きしない。

## 進め方

1. 起点ページを取得し、書かれた事実だけを読む
2. 公式ドキュメント（API リファレンス・CLI help）で仕様を裏取りする
3. 検証題材をユーザーに提案し、合意を得てから書く
   - 汎用リソースより、実運用で使う題材を選ぶ（例: Lambda のログ）
4. 下記テンプレートで `memo.md` を書く
5. ユーザーの文書コメントに対応する（後述）

## 記述ルール

- 本文は日本語、端的に。体言止め・短い述語。前置きや同内容の言い換えを避ける
- 出典 URL は該当箇所の下に生 URL で置く。インラインリンクにしない
- 公式ドキュメントで裏取りした事実と、推測を分ける。推測・未検証は明記する。裏が取れない記述は載せない
- コマンドは help / 公式ドキュメントで実在を確認したものだけ書く。確認できないコマンド・パラメータ・画面操作は「未確認（実機で確認）」と明記する。画面名やオプションを推測で書かない
- 検証範囲の線引き: 実測した範囲だけを「やったこと」と書く。未実測は機能紹介レベルとして分ける
- 手順は試行錯誤を書かず、成功パターンで書く。失敗で得た注意点は手順に織り込む
- 環境固有値（アカウント ID など）はブログ掲載時に伏せる前提で扱う

## 構成テンプレート

冒頭に次の 1 行を置く。

```
下書きメモ。清書は blog.md で行う。投稿先ははてなブログ。
```

### 1. きっかけ（アップデート紹介）

- 発表日、機能の概要を箇条書きで紹介（発表文に書かれた事実のみ）
- 末尾に出典の生 URL

### 2. 従来との違い

- 従来 / 今回の比較表（設定単位、手段、既定動作など）
- 公式ドキュメントで確認した、発表文にない仕様を箇条書き。出典の生 URL を付ける

### 3. 検証したいこと

- 発表文に書かれていない点を洗い出して項目化（優先関係・上書き・反映タイミング・対象範囲など）
- 各項目に「期待（推測・未検証）」を併記
- コンソール確認の項目を含める
  - CLI と画面表示が一致するか
  - 設定の由来（新機能か個別設定か）を画面で見分けられるか
  - コンソールから作成できるか
  - 公式ドキュメントで確認できない画面は「未確認」

### 4. 検証シナリオ

最小構成にする。

- リソース数を絞る
- 確認ポイントは 3 点程度
- 記録タイミングも最小（作成直後 / 一定時間後）
- dryRun など事前確認手段があれば本編に入れる
- それ以外は「余力があれば」に 1 項目 1〜2 行で集約。コマンドは省略
- 影響範囲が広い操作（アカウント全体に効く設定など）は注意書きを置き、対象を絞る手段を明記
- 構成表（リソース / 作成タイミング / 確認 / 期待）→ 準備 → 作成 → 確認の順
- コンソールでの確認手順を CLI 手順と併記

### 5. 後片付け

- 作ったリソースの削除手順
- 削除しても残るリソース（自動作成されたログなど）の注意

### 6. 結果

実測した出力を後で貼る前提の空見出しを置く。

- 6-1 作成直後
- 6-2 一定時間後
- 6-3 気づき
- 6-4 コンソール画面のスクリーンショット欄

ブログに載せるエラー文や CLI 応答は抜粋・要約せず、実際の出力をそのまま貼る。伏せるのは IP など最小限。

### 7. 未確認事項

本当に未確認のものだけを列挙する。確認済みになった項目は消す。

## 文書コメントへの対応

ユーザーが `memo.md` にコメントで修正を依頼したとき（「これって何」「もう少し短く」など）:

- 説明が足りない箇所: 書き直し案を示し、合意を取ってから反映する
- 短縮: 省いた項目を明示する
- 指摘箇所以外は変えない
